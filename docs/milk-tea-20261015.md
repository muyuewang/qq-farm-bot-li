## 自动化（本地新增）

上游只给手动操作，本地在 `core/src/services/milk-tea-auto.ts` 里加了定时任务，半小时一轮（登录 90s 后首跑），走 `runExclusiveAutomationTask('milk_tea', ...)` 全局互斥。十一个开关默认全开（用户 2026-10-15 要求，活动进行中就直接跑）：

| 配置键 | 动作 | operate_type | 会不会花东西 |
| --- | --- | --- | --- |
| `milk_tea_claim_rewards` | 领收银台收益 | 59 | 不花 |
| `milk_tea_claim_wages` | 领员工工资 | 64 | 不花 |
| `milk_tea_claim_fund` | 领成长基金已达档位 | 76 | 不花 |
| `milk_tea_happy_daily` | 领本期每日快乐值 | 74 | 不花 |
| `milk_tea_happy_share` | 领本期首次分享 | 70 | 不花 |
| `milk_tea_happy_milestones` | 领本期快乐档位 | 71 | 不花 |
| `milk_tea_craft` | 制作奶茶 | 62 | 消耗果实 |
| `milk_tea_hire` | 雇佣员工 | 57 | 花奶茶券（1041） |
| `milk_tea_upgrade` | 店铺升级 | 61 | 花店内金币 |
| `milk_tea_boost` | 一键爆单 | 60 | 花宣传喇叭（`shop.sales_item_id`） |
| `milk_tea_seed_buy` | 兑换买种子 | 1 | 花兑换货币（不花钻石） |

默认值在 `DEFAULT_ACCOUNT_CONFIG.automation` 里（`core/src/models/store/shared-state.ts`），前端设置页的兜底块同步。已经把这些 key 存成 false 的账号不会被翻回来——`normalizeAccountConfig` 只在该项从没出现在配置里时才继承默认，所以「默认开启」对新账号和奶茶 key 还没落地前就存过配置的账号生效，对主动关掉的账号不生效。

十一项在一轮里串行执行，步骤间隔 800ms（`MILK_TEA_TASK_SPACER_MS`），不做并发；一轮最多同时只有一个请求在飞（三个快乐值领取合为一步，步骤内部也已经是排队）。整个活动自动化又被 `runExclusiveAutomationTask('milk_tea', ...)` 串在同一把锁上，不会和神秘商人重叠。

判断依据只用服务端返回的状态：`pending_rewards` 有数量才领收益，`work.slips[].wage_status === 1` 才领工资，基金 `unlocked` 且有 `state === 2` 的档位才领基金，快乐不独享按 `daily_reward_claimed`／`first_share_awarded`／档位 `state` 决定。活动不在开放期、店铺还没开业、这一项没得领，都只记一行按天去重的跳过日志，不发写请求。快乐不独享的实例 id 从 `share-reward-instances.json` 由新到旧找当前开着的那一期，不写死 `2026110104`。

后五项会花东西，选法按 2026-10-15 用户给定的口径：

- 制作：按背包顺序取「配方已解锁、未被仓库锁定、有库存」的果实，整堆提交（服务端要求每堆数量与刚读到的一致），同一种果实的多堆并成一批以免一次请求里混不同果实，每批最多 20 堆、每轮最多 6 批，剩下的下一轮接着做，批次之间隔 400ms 不占满连接。`uid` 和数量原样交给服务端，制作前 `milk-tea.ts` 会重读工坊页，中途变了报「果实数量或锁定状态已变化」而不是做错。
- 雇佣：读 `hireList` 时按活动页默认的最短一档 `duration_id=1`（4 小时），工资与位消耗都按这一档报价；员工位取第一个已解锁且当前没人当班的位置（解锁数量看 `MilkTeaStoreLevelConfig.employee_slot_count`），候选人只在 `hire.friends` 里挑，`state === 0` 且已过 `rehire_available_at` 的算可雇，机器人候选不算好友；随机取一个。发之前先看奶茶券够不够 `wage_total`、剩余营业时间够不够一个班次，都不满足只记跳过。
- 升级：只在 `summary.can_upgrade` 为真时发，并把刚读到的 `summary.level` 作为 `expectedLevel`，期间等级变了由服务端拒。
- 爆单：用量 = 待售杯数（`pending_cups_by_recipe` 求和）÷ 单个喇叭出杯数（`boost_cups_per_use`）向上取整，再按持有量和官方单次上限 9999 夹住；没有待售杯就不花喇叭。
- 兑换购买：只买 `category_tag === 'seed'` 的种子，按 `ShopGoodsInfo.order`（官方列表顺序）从前往后取第一个「`available`、成本不是钻石、`diamond_cost_count` 为 0、当前余额付得起」的，一次 1 件、一轮最多一件。`available` 已经把限购买满、解锁条件未满足、结算期不能买种子三种情况算进去了；`costs` 原样作为 `expectedCosts` 交给服务端，价格变了会被 `checkCost` 拒掉而不会按旧价买。背包里读不到的货币（金币在仓库里可能是 id 1 而不是 1001）按付不起处理，只记跳过，不会误买。

五项都要活动开放且不在结算期（`settling` 或 `shop.is_settling`）。

不做自动开关的：开业和改名（要用户起店名）、兑换里的非种子商品（要用户挑东西）、成长基金解锁（要确认付费）、工作互动（要选互动类型 1—5）、躺平模式开关（要决定自己出去不打不打工）、排行榜与营业记录（只读）。这些要么缺一个该由用户做的主意，要么缺实服证据——挂一个什么都不执行的开关比没有开关更坏。

同一轮里各项彼此隔离：某项写失败只记错误日志，不会带走后面的领取，也不会自己重试（回包不完整时 `operateMilkTeaActivity` 已保证不重发，多领一次、多花一次货币都退不回来）。
